# 第2章  总体设计

## 2.1  需求概述

系统面向中国农业大学东西两校区师生，提供一个基于微信小程序的校园闲置物品交易平台。核心约束：

- 仅限 `cau.edu.cn` 邮箱认证用户，保障交易安全
- 平台不介入任何资金流转，所有交易均为线下面交
- 以「4位取货码」核销机制实现交易闭环
- 诚信分与阶梯限权构建校园风控体系
- 支持东西校区属地化展示与跨区交易意向标识

## 2.2  设计原则

| 原则         | 说明                                                |
| ------------ | --------------------------------------------------- |
| 安全优先     | 所有涉及用户身份、交易核销的操作必须经过身份验证    |
| 最小权限     | 依据认证等级（L0/L1/L2）按需开放权限                |
| 前后端分离   | 微信小程序前端 + RESTful 后端 API，解耦便于独立迭代 |
| 高内聚低耦合 | 六大功能模块各司其职，通过统一接口层交互            |
| 可扩展性     | 架构预留广告位、商家入驻、权重置顶等未来扩展接口    |
| 数据脱敏     | 统计报表仅使用聚合数据，不暴露个人隐私              |

## 2.3  技术选型

| 层次     | 技术方案                                                                 | 选型理由                                                 |
| -------- | ------------------------------------------------------------------------ | -------------------------------------------------------- |
| 前端     | 微信小程序（WXML + WXSS + JS）                                           | 微信生态原生，无需额外安装，用户门槛低                   |
| 后端     | Node.js + Express 或 微信云开发                                          | 轻量，契合小程序云开发生态，支持快速迭代                 |
| 数据库   | MySQL 8.0（关系型）+ Redis 7.x（缓存）                                   | 结构化业务数据 + 高频读取缓存（商品列表、验证码）        |
| 即时通讯 | **WebSocket（wx.connectSocket）或微信云开发实时数据监听（watch）** | 实现站内IM消息秒级推送，避免HTTP短轮询对服务器造成的压力 |
| 文件存储 | 微信云存储 / 对象存储（OSS）                                             | 商品图片、视频文件存储，CDN加速                          |
| 消息推送 | 微信订阅消息（服务通知）                                                 | 交易状态变更、逾期提醒等消息通知                         |
| 邮件服务 | SMTP（阿里云邮件推送 / 腾讯邮件）                                        | CAU邮箱验证码发送                                        |
| AI接口   | 大语言模型API（预留）                                                    | 商品描述生成、智能分类、违规内容检测                     |

# 第3章  系统架构设计

## 3.1  系统分层架构

系统采用经典四层架构（表现层、业务逻辑层、数据访问层、数据持久层），各层职责清晰：

![图](./1.png)

| 层次                      | 组成                                                              | 主要职责                                                   |
| ------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------- |
| 表现层（Presentation）    | 微信小程序页面（Pages）+ 自定义组件（Components）                 | 负责UI渲染、用户交互、前端状态管理、调用后端API            |
| 业务逻辑层（Service）     | 后端各模块Service类（Auth、Item、Chat、Order、Credit、Analytics） | 实现核心业务逻辑，如认证流程、取货码生成与核销、诚信分计算 |
| 数据访问层（Repository）  | 各模块DAO / ORM模型                                               | 封装数据库查询与更新操作，屏蔽SQL细节                      |
| 数据持久层（Persistence） | MySQL主库 + Redis缓存 + 对象存储                                  | 持久化存储业务数据；Redis缓存验证码、Session、热门商品列表 |

## 3.2  总体部署架构

部署方案采用「微信小程序前端 + 独立后端服务器 + 云存储」三端分离方式：

![图](./2.png)

各部署节点说明：

- **微信客户端**：运行小程序，通过HTTPS调用后端API；通过微信订阅消息接收通知
- **后端服务器**：部署于云服务器（或微信云开发环境），提供RESTful API，连接MySQL与Redis
- **云存储**：商品图片、视频通过前端直传至OSS/云存储，后端仅保存URL引用
- **邮件网关**：后端调用SMTP服务发送验证码邮件至 `cau.edu.cn` 邮箱
- **管理后台**：独立Web管理页面（与后端共享API，权限隔离），供管理员审核、统计使用

## 3.3  功能模块总览

系统共划分为以下6个核心功能模块，各模块对应SRS第三部分的需求规格：

| 模块编号 | 模块名称           | 对应SRS章节 | 核心职责                               |
| -------- | ------------------ | ----------- | -------------------------------------- |
| M1       | 用户接入与身份认证 | 3.1         | 微信登录、CAU邮箱验证、三级权限管理    |
| M2       | 商品发布与管理     | 3.2         | 商品CRUD、图片上传、状态机管理、AI辅助 |
| M3       | 求购与信息互助     | 3.3         | 求购帖发布、`我有它`响应、智能推送   |
| M4       | 交易闭环与隐私安全 | 3.4         | 站内IM、取货码核销、租赁履约、跨区策略 |
| M5       | 个人中心与风控管理 | 3.5         | 诚信分、黑名单、异常监控、管理员后台   |
| M6       | 数据统计与报表分析 | 3.6         | 实时仪表盘、多维报表、数据导出         |

# 第4章  模块与功能设计

## 4.0  模块依赖关系

系统六大功能模块之间的依赖关系如下：


![图](./3.png)



| 依赖方向 | 说明 |
| -------- | ---- |
| M1 → M2/M3/M4/M5/M6 | 所有模块均依赖 M1 的 JWT Token 认证与 auth_level 权限校验 |
| M2 → M3 | 卖家发布商品时触发 `MatchNotifyService`，向匹配的求购者推送提示 |
| M2 → M4 | 商品信息是交易（取货码生成）的起点 |
| M3 → M4 | "我有它"响应引导至 IM 私聊 |
| M4 → M5 | 交易结果（完成/取消/逾期）作为诚信分加减的输入 |
| M4 → M6 | 交易流水是统计报表的核心数据源 |
| M5 → M4 | 诚信分阶梯限权影响交易模块的可用操作 |

## 4.1  M1 用户接入与身份认证模块

#### 邮箱解绑与强制覆盖机制

针对 `一个cau.edu.cn邮箱仅能绑定一个微信OpenID`可能带来的**独占性漏洞**（学生换微信后旧邮箱永久锁死），在 EmailVerifyService 中采用以下逻辑：

- **解绑申诉流程**：已认证用户可提交"换绑申请"，系统向原邮箱发送确认链接。原邮箱点击确认后释放绑定关系，新微信方可绑定。
- **强制覆盖机制（封闭场景兜底）**：若原邮箱长期无活动（> 180天未登录），且新用户提供与邮箱前缀匹配的学号证明，管理员可通过后台强制覆盖旧绑定。
- **毕业生过渡期**：毕业年份的7月1日起，毕业生认证记录的绑定锁定自动降级为"可申请换绑"状态，避免离校学生邮箱被永久锁定。

#### 毕业后等级自动降级机制

针对毕业生实施身份复核与自动降级：

- **定时扫描**：每年7月1日凌晨，系统定时任务扫描 `t_user` 表中 `auth_date` 字段
- **降级判定条件**：满足以下任一条件则触发降级：
  - `DATEDIFF(NOW(), auth_date) > 1460`（认证距今超过4年，即本科已毕业）
  - `is_staff = false` 且系统记录的毕业年份（`graduation_year`）≤ 当前年份
- **降级处理**：将 `auth_level` 从 L1/L2 自动降为 L0，记录降级原因与时间戳至 `t_credit_log`
- **重新认证**：降级后用户可重新提交学籍证明（如研究生在读证明）恢复等级
- **前端通知**：降级生效时，前端在用户下次登录时弹出"身份确认"弹窗

#### 独立二级密码（SecurityPasswordService）

用户可设置独立于微信的6位二级密码：

- **密码规则**：6位纯数字，BCrypt加盐哈希存储于 `t_user.security_password_hash`
- **触发场景**：
  - 点击「确认交易/面交」按钮时，要求输入二级密码（如已设置）
  - 修改绑定手机号、邮箱等敏感信息时
  - 申诉账号恢复时
- **重置流程**：通过绑定的 CAU 邮箱接收验证码后重置二级密码（无需旧密码）
- **安全策略**：同一设备3次输入错误锁定30分钟

### 4.1.3  关键流程

登录与认证主流程：

- **Step 1**：前端调用 `wx.login()` 获取临时 code
- **Step 2**：后端以 code 换取 OpenID，查询/创建用户记录
- **Step 3**：用户填写 `@cau.edu.cn` 邮箱，后端正则校验并发送6位验证码（有效期5分钟）
- **Step 4**：用户输入验证码，后端比对成功后将 `auth_level` 升级至 L1
- **Step 5**：用户补充学号/姓名/证件核验，升级至 L2
- **Step 6**：引导用户选择所属校区，更新 `campus_area` 字段

### 4.4.3  取货码核销流程

#### 核销时序图

![图](./5.png)



#### 流程步骤说明

- **Step 1**：双方在聊天窗口点击「确认交易/面交」
- **Step 2**：系统为买家生成唯一4位取货码，**使用 `SELECT ... FOR UPDATE` 行级锁强制校验商品状态必须为 `Active`**（防止孤品超卖），关联交易订单，有效期24小时
- **Step 3**：线下见面，买家出示取货码（可生成离线凭证卡片委托他人代领）
- **Step 4**：卖家在小程序输入4位码，后端校验匹配
- **Step 5**：商品状态从 `Reserved` → `Sold`，买家收到「交易完成」服务通知

#### 孤品超卖防护机制

校园二手交易场景下，绝大多数商品为"孤品"（数量仅为1）。高并发时多个买家可能同时对同一商品点击"确认交易"，存在**一货多锁**的超卖风险。设计如下：

- **行级悲观锁**：在 `TokenService` 生成取货码时，执行 `SELECT ... FROM t_item WHERE item_id = ? FOR UPDATE`，对目标商品行加排他锁，阻断其他并发请求对该行的修改。
- **状态双重校验**：锁住行后必须再次校验 `item_status = 'Active'`，若状态已变更（已被他人锁定或已售出），则直接拦截并返回错误提示。
- **辅助方案**：对热门商品引入Redis分布式锁（`SETNX` + TTL），在应用层快速过滤掉明显冲突的请求，减轻数据库锁竞争压力。

### 4.4.4  租赁双阶段核销流程

针对租赁履约与状态流转要求，租赁交易区别于一次性买卖，采用"借出核销+归还核销"双阶段闭环：

#### 第一阶段：借出核销

1. 双方线下见面查验物品（如四六级耳机是否出声）
2. 买家线下向卖家转交押金与租金后，卖家在小程序输入系统为买家生成的 **4位借出核销码**
3. 后端校验通过后：
   - `t_transaction.transaction_type` → `Rental`
   - `t_transaction.rental_status` → `Renting`（租赁中）
   - `t_transaction.expected_return_time` → 当前时间 + 约定租期
   - 系统开始计时
4. 卖家收到"租赁已生效"服务通知

#### 第二阶段：归还核销

1. 租期届满，双方再次碰头
2. 买家归还物品，卖家检查无损坏后线下退还押金
3. 卖家向买家出示系统为其生成的 **4位归还确认码**，买家在小程序输入
4. 后端校验通过后：
   - `t_transaction.rental_status` → `Returned`（已归还）
   - `t_transaction.finish_time` → 当前时间
   - 对应商品 `t_item.item_status` → `Sold`
5. 双方收到"租赁已完结"服务通知

#### 逾期与风控

- **超期提醒**：租期结束前12小时，系统自动推送微信服务通知提醒双方
- **逾期处理**：若归还时间超过 `expected_return_time`，买家仍可归还，但系统记录逾期标记
- **违约惩罚**：若买家逾期拒不归还或造成物品严重损坏，卖家可发起"租赁仲裁"：
  - 管理员核实后，违约方直接被扣 **50 校园诚信分**（触发黑名单机制）
  - 违约方的部分脱敏信息将公示于平台公告


![图](./6.png)



#### 异常处理

- 输入错误3次锁定交易10分钟
- 超24小时自动失效，引导双方重新沟通

### 4.5.4  诚信分变动轨迹

依据 SRS F5.2.3 透明度要求，用户可在"个人中心"查看自己的信用分变动轨迹（类似账单记录）：

- **数据存储**：每次加减分操作写入 `t_credit_log` 表，记录操作时间、变动金额、变动原因、关联管理员
- **前端展示**：按时间倒序展示，每条记录包含：
  - 变动日期时间
  - 变动分数（绿色 + 加分 / 红色 − 减分）
  - 变动具体原因（如"完成一次好评交易+2"、"确认面交后单方取消-10"）
  - 变动后当前分数
- **查询接口**：`GET /api/v1/users/:id/credit/log`，支持分页与时间范围筛选

### 4.5.5  浏览历史回看

保存用户最近浏览记录：

- **数据存储**：`t_browse_history` 表记录用户每次点击商品详情的行为，每个用户最多保留最近 20 条记录（FIFO淘汰）
- **前端入口**：个人中心 →「最近浏览」Tab，以时间倒序展示最近点击的 20 个商品
- **查询接口**：`GET /api/v1/users/:id/history`，返回商品缩略图、标题、价格、浏览时间
- **去重策略**：同一用户对同一商品的重复浏览仅更新浏览时间，不新增记录

### 4.5.6  黑名单系统

依据 SRS F3.5.3 要求：

- **个人黑名单**：用户 A 可将用户 B 添加至个人黑名单 `t_blacklist` 表。黑名单内用户无法查看 A 发布的商品、无法向 A 发起聊天。
- **平台级黑名单**：同一用户 24 小时内被 ≥ 3 个不同用户举报，系统自动临时锁定账号并进入管理员待审序列。
- **身份熔断**：被永久封禁的 `cau.edu.cn` 邮箱及对应学号永久无法再次注册。

# 第7章  非功能设计约束

## 7.1  性能设计

| 性能目标                           | 技术方案                                                  |
| ---------------------------------- | --------------------------------------------------------- |
| 商品列表页加载 ≤1.5秒（主流设备） | Redis缓存热门商品列表；图片懒加载；OSS CDN加速            |
| 搜索反馈 ≤1.8秒                   | MySQL全文索引或Elasticsearch（后期可扩展）；Redis缓存热词 |
| 支持500+并发在线                   | 后端无状态横向扩展；连接池复用；读写分离（可选）          |
| 统计报表无实时压力                 | 每日凌晨 ETL 离线预聚合，写入 t_stats_daily               |

## 7.2  安全性设计

### 7.2.1  认证与访问控制

| 安全需求         | 技术方案                                                                  |
| ---------------- | ------------------------------------------------------------------------- |
| 防爆破验证码     | 同邮箱60s内限发1次；同设备每日限验证5次；失败锁定24小时                   |
| 取货码防暴力破解 | 输入错误3次锁定10分钟；HMAC生成，服务端校验                               |
| 防多账号         | 一个 `cau.edu.cn` 邮箱仅能绑定一个 OpenID；邮箱永久封禁机制             |
| 二级密码         | 6位数字BCrypt加盐哈希；确认面交/修改敏感信息需二次验证；3次错误锁定30分钟 |

### 7.2.2  数据安全

| 安全需求     | 技术方案                                                   |
| ------------ | ---------------------------------------------------------- |
| 敏感数据加密 | 手机号、学号 AES-256 加密存储；全链路HTTPS（TLS 1.2+）传输 |
| 图片水印防盗 | 服务端对所有上传图片合成半透明水印，防爬虫诈骗             |

### 7.2.3  接口安全

| 安全需求     | 技术方案                                                        |
| ------------ | --------------------------------------------------------------- |
| 反刷接口     | 发布和验证接口限流（滑动窗口算法）；每日发布上限5条             |
| 交易并发安全 | 生成取货码时使用 `SELECT ... FOR UPDATE` 行级锁，阻止孤品超卖 |
| 认证令牌     | JWT Bearer Token，有效期7天，过期需重新登录                     |

### 7.2.4  内容安全

| 安全需求   | 技术方案                                           |
| ---------- | -------------------------------------------------- |
| 关键词过滤 | NLP规则拦截"代做"、"快递"、"邮寄"等违规关键词      |
| AI违规检测 | OCR/图像分类模型自动拦截含联系方式、违规广告的图片 |
| 举报机制   | 多举报自动触发临时锁定，进入管理员待审序列         |

## 7.3  隐私设计

- 用户手机号/微信号默认脱敏显示（`138****5678`），交易意向确认后可选择性披露
- 站内聊天内容仅交易双方可见，平台服务端加密存储，管理员不可直接查阅
- 统计报表所有数据均为脱敏聚合数据，不关联具体用户隐私
- 报表功能仅限 `admin` 角色访问，通过 RBAC 权限控制隔离

## 7.4  可靠性与可用性设计

### 7.4.1  事务一致性

交易核销操作采用数据库事务（ACID），保证取货码状态与商品状态变更的原子性。具体地：

- 取货码核销操作包装在 `BEGIN TRANSACTION ... COMMIT` 中
- 同时更新 `t_item.item_status` 和 `t_transaction.token_status`
- 任一操作失败则全部回滚，防止状态不一致

### 7.4.2  数据备份与恢复

| 措施     | 详情                                                         |
| -------- | ------------------------------------------------------------ |
| 自动备份 | 用户数据与交易记录每日自动备份至云存储                       |
| 备份保留 | 保留最近30天全量备份，7天增量备份                            |
| 故障恢复 | 系统故障后 30 分钟内可恢复正常服务（基于云环境自动重启策略） |

### 7.4.3  服务降级策略

| 降级场景       | 处理方式                                                       |
| -------------- | -------------------------------------------------------------- |
| AI接口不可用   | 关闭AI辅助入口，发布流程正常运行（用户手动选择分类和填写描述） |
| Redis不可用    | 降级为直接读MySQL，关闭热门商品缓存层                          |
| 邮件服务不可用 | 提示用户稍后重试，验证码接口返回503                            |

# 第8章  出错处理设计

## 8.1  错误码规范

| 错误码范围 | 类型         | 示例                                                                                                                     |
| ---------- | ------------ | ------------------------------------------------------------------------------------------------------------------------ |
| 1000–1099 | 认证相关错误 | 1001-验证码错误，1002-邮箱已绑定，1003-认证等级不足，1004-二级密码错误，1005-二级密码已锁定                              |
| 2000–2099 | 商品相关错误 | 2001-必填项缺失，2002-图片违规，2003-发布频率超限                                                                        |
| 3000–3099 | 交易相关错误 | 3001-取货码错误，3002-取货码已过期，3003-商品已售出，3004-商品已被锁定（并发冲突），3005-租赁归还码错误，3006-租赁已逾期 |
| 4000–4099 | 权限相关错误 | 4001-未登录，4002-诚信分不足，4003-账号已封禁，4004-认证等级降级                                                         |
| 5000–5099 | 系统内部错误 | 5001-数据库异常，5002-外部服务不可用                                                                                     |

## 8.2  关键异常处理策略

| 异常场景               | 处理方式                                                        |
| ---------------------- | --------------------------------------------------------------- |
| 邮箱验证码超时         | 提示用户重新获取，旧码立即失效                                  |
| 商品自动下架           | 到期前3天推送提醒；到期后状态改为Inactive并通知卖家             |
| 取货码3次错误          | 锁定交易10分钟，超限后引导联系对方或申请仲裁                    |
| 二级密码3次错误        | 锁定30分钟，提示用户可通过邮箱验证码重置                        |
| 毕业后等级降级         | 每年7月1日自动扫描降级，用户登录时弹出"身份确认"弹窗            |
| 统计数据为空           | 显示「暂无数据」而非报错，不影响其他指标展示                    |
| AI接口不可用           | 降级处理：关闭AI辅助入口，发布流程正常运行                      |
| 跨区交易未核销超24小时 | 取货码自动失效，双方收到服务通知，引导重新协商                  |
| 租赁逾期未归还         | 租期届满后系统记录逾期标记，卖家可发起"租赁仲裁"                |
| 并发商品锁定冲突       | 返回提示「该商品已被其他用户锁定，请浏览其他商品」，状态码 3004 |
